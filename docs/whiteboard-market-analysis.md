## 1. 한 줄 정의

수업 주소를 QR·4자리 코드로 열면 **로그인 없이** 학생 PC·모바일이 입장하고, 교수자가 올린 PDF 교안과 실시간 입력 노트·링크를 함께 보며, 학생이 자기 속도로 이동했다가 한 번에 교수자 화면으로 복귀할 수 있는 **수업 동기화 화면**.

## 2. 지금까지 확정한 설계 (질문 12개 응답 결과)

| # | 항목 | 확정 내용 |
|---|---|---|
| 1 | 학생 입장 | QR + 짧은 주소 + 수업코드. 계정 불필요 |
| 2 | 페이지 이동 | 교수 동기화가 기본. 학생은 자유 이동 가능하며, **「교수 화면으로 돌아가기」 버튼과 「내가 작업하던 페이지로 돌아가기」 버튼**으로 학습자가 최종 조절 |
| 3 | 규모 | 전산실 동시 접속 최대 40명, 교수자 1명 |
| 4 | 자료 형식 | PDF 업로드 (PPT는 PDF로 변환해 사용) |
| 5 | 저장소 | 기존 Supabase 프로젝트 재사용 (별도 스키마 + RPC, award·budget와 동일 구조) |
| 6 | 화면 구성 | 자료(PDF) 크게 + 오른쪽 패널. 패널에 교수자가 **한글 편집기처럼 입력하는 노트**(밑줄·글자색 등 가벼운 서식)를 글자 단위로 실시간 표시. **모바일은 공간이 좁으므로 팝업**으로 표시 |
| 7 | 링크 | 수업 중 즉석 링크 푸시 (학생 화면에 바로 나타남) |
| 8 | 학생 기능 | 이해도 신호(이해함/어려움) 집계. 교수자 화면에 인원수 표시 |
| 9 | 교수 화면 | 별도 관리자 화면(`?mode=teacher`) + 빔프로젝터용 학생 화면 보기 |
| 10 | 동기화 수준 | 글자 단위 실시간 (목표 지연 0.3초) |
| 11 | 권한 | 교수 비밀번호 (award·budget와 동일한 RPC 토큰 방식). 학생은 읽기 전용 + 이해도 신호만 |
| 12 | 장애 대비 | 자동 재연결 + 4초 폴링 백업, 연결 상태 표시 |

내일 수업 마감 범위: **PDF + 동기화 + 노트 + 링크 푸시 + 이해도**. 펜 필기·질문 올리기·결과 제출·학생 메모는 다음 회차로 미룸.

## 3. 기술 구조 (사용자 관점 요약)

```
교수 화면(관리) ──비밀번호 RPC──> Supabase (wb 스키마: 수업방, PDF 위치, 노트, 링크, 이해도)
        │                                  ▲
        └── 실시간 전송(Broadcast) ────────┤
                                           ▼
학생 화면 40개 ◄── 실시간 수신 + 4초 폴링 백업(끊김 대비)
PDF 파일: Supabase Storage (공개 읽기) → 브라우저의 PDF.js로 렌더링
```

- 서버 구축·빌드 없음. 기존 정적 웹앱(GitHub Pages) 구조에 파일 1~2개 추가하는 방식
- 교수자 사칭 방지: 실시간 메시지에 교수 토큰을 싣고, 학생 화면은 서버에 저장된 해시와 대조 후에만 반영 (설계안)
- 재사용 자산: Supabase RPC·비밀번호 로그인 패턴, QR 생성(`award-qr.min.js`), PDF.js 3.11.174(award에서 사용 중), 디자인 토큰(`--r:6px`, 아이콘 SVG)

## 6. 강점·약점 (내부 평가)

| 구분 | 내용 |
|---|---|
| 강점 | 계정·설치 없이 QR로 입장. 개인정보 수집이 없는 설계라 규제 부담이 작음. 한글 환경과 한국 수업 현장 용어 반영. 기존 인프라 재사용으로 운영비가 낮음 |
| 약점 | 기능이 대형 서비스와 겹치고 차별 기능이 약함. 개발·운영 인력이 사실상 1인. 모바일·브라우저·학교 네트워크 편차 대응 부담. 현재 미구현이며 실사용 검증 데이터 없음 |
| 기회 | 직업전문학교·학원·기업교육·AI 강의 시장처럼 계정 연동이 어려운 현장. PDF 교안 + 링크·프롬프트 배포가 필요한 AI 활용 교육 |
| 위협 | Google·Microsoft·국내 대형 에듀테크의 무료 제공. 학교의 SW 선정 기준 강화로 신규 사업자의 진입 비용 증가 |

## 7. 기술·운영 리스크 (사업화 시 반드시 검토)

1. **Supabase 한도:** 무료 플랜 실시간 동시 접속 200건·월 메시지 200만 건 수준으로 보도하는 자료와 Pro 200 또는 500건으로 엇갈리는 자료가 있음 → **공식 문서 확인 필요** ([JetAdmin](https://www.jetadmin.io/blog/supabase-pricing-2026-guide-to-plans-limits-and-real-world-costs/), [CloudZero](https://www.cloudzero.com/blog/supabase-pricing/)). 글자 단위 전송은 메시지 수를 크게 늘리므로 사업화 시 전송 간격 조절 필수
2. **공유 프로젝트 위험:** 현재 안은 forum·award·budget와 같은 Supabase 프로젝트를 씀. 상용화 시에는 **프로젝트 분리** 필요 (장애·보안 사고 전파 방지)
3. **공개 저장소 구조:** 학생 접근 키가 공개 anon 키이므로, 교수 권한은 RPC 비밀번호로만 보호됨. 다수 고객이 쓰는 서비스에는 계정·권한 체계 재설계 필요
4. **개인정보:** 익명 설계라 수집이 거의 없으나, 이름 입력·출석 기능을 넣는 순간 학교 SW 선정 기준 대상이 될 수 있음 (추정)
5. **지원 부담:** 수업 시간 중 장애는 즉시 신뢰 손실로 이어짐. 상시 대응 인력 필요

## 8. 사업화 시나리오 (의견)

| 시나리오 | 내용 | 평가 |
|---|---|---|
| A. 내부 도구 유지 | 아세아항공직업전문학교 수업·교육 프로그램에서만 사용 | 가장 현실적. 비용·리스크 최소 |
| B. 유사 기관 무상 보급 + 맞춤 구축 | 직업학교·학원에 설치형/호스팅형으로 제공, 구축비·유지보수비 수취 | 소규모 수익 가능성. 영업·지원 인력이 병목 |
| C. 월 구독 SaaS | 교강사 단위 월정액 | 해외 가격대(연 $120~159, 제3자 자료)와 비교 시 차별화 근거 부족. 단독 SaaS는 비권장 (의견) |
| D. AI 활용 강의 패키지에 결합 | 강의 콘텐츠·교안·프롬프트 세트와 함께 도구 제공 | 도구 단독보다 콘텐츠 결합이 설득력 있음. 방시원님의 전문 분야(AI 활용, 교재 개발)와 정합 |

**판단(의견):** 도구 단독 사업화보다는 **D(콘텐츠 결합) 또는 B(소규모 맞춤)** 가 현실적임. 단독 SaaS는 대형 서비스의 무료·저가 제공과 학교 SW 선정 기준 부담을 감안하면 우선순위가 낮음.

## 9. 사업화 전 검증 순서 (제안)

1. 2026-10-20 수업 실사용 → 접속 성공률, 지연, 이해도 신호 사용률, 학생·교수 피드백 기록
2. 같은 도구를 다른 수업 2~3회 반복 사용 → 재사용 의향 확인
3. 직업전문학교·학원 담당자 5~10곳 인터뷰 → 지불 의사·기존 도구·구매 절차 확인
4. Supabase 공식 한도 확인 및 부하 시험 (40명 → 100명)
5. 학교 SW 선정·개인정보 기준, 조달 등록 요건 공문으로 확인
6. 위 결과로 시나리오 A~D 중 선택

## 10. 다른 창에 던질 마케팅 평가 질문 (복사용)

> 위 자료를 기준으로 다음을 평가해 주십시오.
> 1. 「무로그인 + QR + PDF 교안 동기화 + 이해도 신호」의 차별성이 직업교육·학원·기업교육 시장에서 구매 이유가 되는가
> 2. 목표 고객(교강사 개인 / 학교·학원 기관 / 교육업체) 중 가장 지불 의사가 높은 쪽과 근거
> 3. 시나리오 A~D별 수익 구조와 6개월 내 검증 가능한 지표
> 4. 이름·슬로건·핵심 메시지 후보 (공식 문어체, 과장 표현 제외)
> 5. 학교 개인정보·SW 선정 기준 환경에서의 영업 장애물과 대응 문구
> 6. 근거가 부족한 부분에 대해 추가로 확인해야 할 자료
